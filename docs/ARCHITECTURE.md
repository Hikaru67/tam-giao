# Kiến trúc Backend — Tâm Giao

Clean Architecture + Modular Monolith, TypeScript. Tài liệu này là nguồn chân lý về thiết kế;
luật bắt buộc rút gọn nằm ở `AGENTS.md` mục 2.

## 1. Tổng quan hệ thống

```
Mobile (Expo) ─┐
Admin (Next.js)├─ HTTPS / WebSocket ─► apps/api (Hono) ──┬─ PostgreSQL (schema theo module, outbox)
Partner web ───┘                                        ├─ Redis (pub/sub chat, từ Sprint 6)
                                                        ├─ Object storage S3 (bucket public-profile / private-kyc)
                      apps/worker (pg-boss) ◄── outbox ─┘
                      job hết hạn, relay event, push, retention
Bên ngoài: SMS OTP · eKYC · Cổng thanh toán · Push (Expo/FCM/APNs) · KMS
```

## 2. Các lớp và quy tắc phụ thuộc

```
infrastructure ─► application ─► domain ─► kernel
presentation   ─► application
(phụ thuộc chỉ hướng vào trong)
```

| Lớp | Chứa | Được import |
|---|---|---|
| `domain` | Aggregate, Entity, Value Object, Domain Service, Domain Event, mã lỗi | `@tamgiao/kernel`, `@tamgiao/contracts/constants` |
| `application` | Use case, Query, Port (interface), Facade cho module khác | `domain`, `kernel`, `contracts/constants`, `@tamgiao/module-<khác>/facade` |
| `infrastructure` | Repository (Drizzle), adapter bên ngoài, mapper, schema DB, job handler | tất cả ở trên + thư viện |
| `presentation` | Route Hono, WS handler, map DTO ↔ command, map lỗi → HTTP | `application`, `contracts` |

## 5. Máy trạng thái Match

```
OFFERED ──accept(1 bên)──► AWAITING_RESPONSE ──accept(bên còn lại)──► DATING ──date xong──► MET
  │ decline / hết 24h          │ decline / withdraw / hết 24h            │ stop / hết 14 ngày      │ feedback
  ▼                            ▼                                         ▼                         ▼
EXPIRED | DECLINED          DECLINED | EXPIRED                      CLOSED_STOPPED          CLOSED_SUCCESS (cả 2 chọn A)
                                                                     → COOLDOWN 7 ngày       CLOSED_STOPPED (≥1 chọn B)
Mọi trạng thái chưa đóng ──ReportFiled──► LOCKED
```

- **Độc quyền 1-1:** bảng `matching.active_slots(user_id PK, match_id)`. Tạo match = insert 2 dòng trong cùng `tx`; trùng → `USER_BUSY`. Đóng match = xoá 2 dòng.
- **Cooldown:** `matching.cooldowns(user_id PK, until)`.
- **Hết hạn:** mỗi lần chuyển trạng thái có hạn → `Scheduler.schedule(tx, matchExpiryJob(match))` (queue `matching.expire-match` = `MATCH_EXPIRY_QUEUE`, key `<matchId>:<version>`, `runAt = expiresAt`, payload `{matchId}`); job gọi `ExpireMatch` (kiểm tra lại state + thời gian, idempotent).
- **Bảng match (BE-S5-04):** `matching.matches` — đủ cột dựng lại `MatchState`: hai người lưu 2 cột `user_a`/`user_b` (giữ thứ tự lúc đề xuất; cặp luôn đúng 2 người nên CHECK `user_a <> user_b` và index btree từng cột đơn giản hơn mảng), `created_by` (admin), `status` (CHECK 9 trạng thái), `accepted_by uuid[]` (≤ 2), `score_snapshot` jsonb `{total, pillars}`, `staff_note` (có thể PII — không log, không vào event/audit), `expires_at` nullable, `offered_at`/`dating_started_at`/`met_at`/`closed_at`, `declined_by`, `decline_reason`, `withdrawn`, `close_outcome` (CHECK), `lock_reason`, `updated_at`, `version`. `DrizzleMatchRepository.save` kiểm tra version lạc quan (version trước = version − số event chờ: `0` → INSERT, khác → `UPDATE … WHERE version = <trước>`, lệch → throw) rồi ghi mỗi event một dòng `matching.match_events` (`id` = eventId, `match_id` FK, `event_type`, `payload` jsonb như outbox, `occurred_at`, `version`, unique (`match_id`, `version`); **append-only**: trigger cấp câu lệnh chặn UPDATE/DELETE như `billing.ledger_entries`) + outbox, cùng `tx`. Có `findById`, `findByIdForUpdate` (`FOR UPDATE`), `findOpenByUser`.
- **Đề xuất ghép đôi (BE-S5-04):** use case `ProposeMatch` (`createMatchingModule(...).commands.proposeMatch`; route admin + permission `match:propose` ở BE-S5-07). Thứ tự: cùng một người → `MATCH_SAME_USER`; id không phải UUID v7 → `INVALID_ID`; chưa xác thực → `USER_NOT_VERIFIED` (`meta.userIds`) — đọc `VerificationFacade.isVerified` (nguồn chân lý, ngoài transaction) thay vì cờ `verified` của read model (đồng bộ trễ qua event); rồi **một transaction**: chưa có hồ sơ đồng bộ trong `candidate_profiles` → `CANDIDATE_PROFILE_NOT_FOUND` (`meta.userIds`); vi phạm `passesHardFilters` → **chặn** `HARD_FILTER_MISMATCH` (tiêu chí bắt buộc do chính người dùng đặt, chuyên viên không vượt); cooldown → `USER_COOLING_DOWN`; `pair_history` → `PAIR_ALREADY_TRIED`; `CompatibilityScorer` → snapshot; `Match.offer` → `activeSlots.claim([A,B])` (bận → `USER_BUSY`, Err → rollback: không match, không job) → `matches.save` (+ `match_events` + outbox `MatchOffered`) → job hết hạn → audit `match.propose` (meta `{participantIds, scoreTotal, hasStaffNote}`, không ghi nội dung ghi chú; audit bị từ chối → throw, rollback). Hai chuyên viên đề xuất đồng thời cho cùng một người → PK `active_slots` cho đúng 1 thành công.
- **Phản hồi lời ngỏ + hết hạn (BE-S5-05):** use case `AcceptOffer`, `DeclineOffer` (lý do tuỳ chọn, trim, rỗng → `null`; chỉ lưu `decline_reason`, không log/event), `WithdrawIntro` (`createMatchingModule(...).commands.*`) nhận chỉ `userId` (route `POST /me/match/accept|decline|withdraw` không có id; độc quyền 1-1 bảo đảm mỗi người tối đa một match mở). **Một transaction**: `findOpenByUser` (không có → `NO_OPEN_MATCH` 404) → `findByIdForUpdate` (tuần tự hoá với job hết hạn / bên kia bấm cùng lúc; nếu job hết hạn đã thắng khoá → `OFFER_EXPIRED`, cùng mã với người thắng khoá nhưng đã quá hạn) → domain → `save` → `applyMatchTransitionEffects`. Job `matching.expire-match` gọi `ExpireMatch.executeIn(tx, {matchId})` (worker: `createExpireMatchJob` + `apps/worker/src/jobs/match-expiry.ts` qua `registerJob`): khoá `FOR UPDATE`, `expire(now)`; đã đóng / `MET` → `ALREADY_CLOSED`, job cũ (đã có hạn mới) → `NOT_YET_EXPIRED`, không thấy match → `NOT_FOUND` — đều no-op (A9). **Hiệu ứng chuyển trạng thái** (`applyMatchTransitionEffects`, cùng `tx`, chỉ khi trạng thái đổi): vào `AWAITING_RESPONSE`/`DATING` → hẹn `matchExpiryJob` (khoá theo version mới); vào **mọi** trạng thái đóng (`DECLINED`, `EXPIRED`, `CLOSED_STOPPED`, `CLOSED_SUCCESS`, `LOCKED`) → `activeSlots.release` + `pairHistory.record(outcome = trạng thái cuối)`; `CLOSED_STOPPED` (dừng hoặc hết `DATING_DAYS`) → thêm `cooldowns.start` cho cả hai tới `now + COOLDOWN_DAYS`. Use case sau (feedback BE-S7-03, khoá do báo cáo) dùng lại hàm này.
- **Query màn ghép đôi (BE-S5-06, `createMatchingModule(...).queries`; route ở BE-S5-07):** `getCurrentMatch` (`GetCurrentMatchForUser`, màn 7/9) — match mở qua `MatchRepository.findOpenByUser`; không có → `null`; trả `status`, `phase` nhìn từ người xem (`NEEDS_MY_RESPONSE` = `OFFERED`; `AWAITING_RESPONSE` → `WAITING_FOR_COUNTERPART` nếu mình đã đồng ý / `COUNTERPART_ACCEPTED` nếu đối phương đã đồng ý; `DATING`; `MET`), `expiresAt` = đúng `matches.expires_at`, điểm tổng + 3 trụ cột từ `score_snapshot`, `staff_note` (chỉ người trong cặp), thẻ đối phương. `getMatchProfile` (`GetMatchProfile`, màn 8) — theo `matchId` hoặc match đang mở; thứ tự: id sai → `INVALID_ID`, không có → `NOT_FOUND`, **không thuộc cặp → `NOT_PARTICIPANT`** (trước khi xét trạng thái), match đã đóng → `NOT_FOUND`. **Luật hiển thị cho người dùng app** (`application/queries/match-display-rules.ts`): chỉ phần công khai của hồ sơ — tên gọi (`displayNameOf`: bỏ họ khi ≥ 3 từ, như thiết kế "Minh Trang, 28"; không trả họ tên đầy đủ), tuổi, giới tính, thành phố, nghề, học vấn, tự bạch, sở thích, ảnh hồ sơ (presigned GET `publicProfile`); không bao giờ trả SĐT, CCCD, thu nhập/nhà ở/tài sản, ảnh eKYC; phần riêng tư "mở sau bước đồng ý" chưa trả — tách thành task BE-S7-10 (BLOCKED chờ PO/pháp lý); đối phương chỉ thấy tên gọi (PO chốt). **Điểm chung** không lưu trong snapshot → tính lại bằng `CompatibilityScorer` trên read model `candidate_profiles` lúc đọc (thiếu hồ sơ → rỗng); phía người dùng bỏ `SAME_RELIGION` (tôn giáo là dữ liệu nhạy cảm theo NĐ 13), admin thấy đủ. Hồ sơ hiển thị lấy qua facade profile `getMatchDisplayProfiles(userIds, {photos: 'all'|'primary'})` (chỉ hồ sơ `COMPLETED`, chỉ cột không mã hoá). Admin: `listCandidates` (`ListCandidates`) = `FindCandidates` + hồ sơ hiển thị (họ tên đầy đủ, tuổi, thành phố, nghề, học vấn, ảnh đại diện; mặc định 20, tối đa 50); `getMatchesBoard` (`GetMatchesBoard`, port `MatchBoardQuery` → `DrizzleMatchBoardQuery`) lọc trạng thái (mặc định 4 trạng thái mở), sắp `expires_at ASC NULLS LAST, id ASC`, cursor keyset `{expiresAt|null, id}` (presentation mã hoá), tên hai người qua `getApplicantSummaries`, không trả `staff_note`/lý do từ chối.
- **Route HTTP matching (BE-S5-07, `createMatchingModule(...).routes`, `presentation/match-routes.ts` + `match-admin-routes.ts`):** chỉ parse DTO (`@tamgiao/contracts` matching: `dto.ts`, `admin-dto.ts`, `route-dto.ts`) → gọi use case/query → map kết quả (`Date` → ISO); lỗi → Problem JSON theo registry. Người dùng app (`requireUser`, composition root truyền `MatchingModuleDeps.requireUser`): `GET /me/match` (`{match: null}` khi không có match mở), `GET /me/match/profile?matchId=` (bỏ trống = match đang mở), `POST /me/match/accept`, `POST /me/match/decline` (body tuỳ chọn `{reason?}` ≤ `MATCH_DECLINE_REASON_MAX_LENGTH` = 500; không body = không lý do), `POST /me/match/withdraw` — ba nút trả `{matchId, status, expiresAt|null}`. Admin (`requireAdmin('match:propose')` cho cả ba — xem ứng viên/bảng theo dõi là việc của chính chuyên viên mai mối, không thêm permission đọc riêng): `GET /admin/users/:id/candidates?limit=` (≤ 50), `POST /admin/matches` (body `{userAId, userBId, staffNote?}`, `staffNote` ≤ `MATCH_STAFF_NOTE_MAX_LENGTH` = 1000; `staffId` = admin đăng nhập, IP client vào audit; 201 `{matchId, status, participantIds, score, expiresAt}`), `GET /admin/matches?status=&cursor=&limit=` (cursor mờ base64url của `<expiresAt ISO | ->|<id>`, `-` = dòng không có hạn; cursor hỏng → 422). Mọi mã lỗi owner `matching` có status 4xx trong registry (test `matching-http-errors.test.ts`).

Messaging đóng hội thoại khi nhận `MatchLocked` (BE-S6-01). `match_id` của báo cáo không khai FK sang `matching.matches` (A3).

## 6. Pattern hạ tầng

- **UnitOfWork:** `uow.run(async tx => …)` bọc `db.transaction`.
- **Outbox:** `outbox(id, event_type, payload, occurred_at, published_at)`; worker relay → EventBus nội bộ → handler; `processed_events(consumer, event_id)` đảm bảo idempotent.
- **Scheduler:** pg-boss, job key = `<type>:<aggregateId>:<version>` để không trùng (`PgBossScheduler`: id job = UUID v5 của `<queue>:<key>`, gửi bằng chính connection của `tx` → rollback thì không có job). **API** (từ BE-S5-04) dựng một instance pg-boss **chỉ để gửi job** (`apps/api/src/job-scheduler.ts`: `supervise: false`, `schedule: false`, không worker; `migrate` mặc định) và tạo sẵn các queue mà API gửi (`MATCHING_SCHEDULED_QUEUES`) cùng cấu hình `ensureQueue` của worker (`DEFAULT_RETRY_POLICY` + dead-letter `<queue>.dead`; `createQueue` là `ON CONFLICT DO NOTHING`), đóng khi shutdown. Worker chạy handler + bảo trì.
- **Encryptor:** envelope encryption AES-256-GCM; master key từ KMS (local: env). Blind index HMAC-SHA256 cho tìm kiếm CCCD.
- **Storage:** presigned PUT/GET; bucket `public-profile` (ảnh hồ sơ, vẫn cần auth để lấy URL) và `private-kyc` (CCCD, selfie, bằng chứng). Port `ObjectStorage` + `UploadRegistry` ở `@tamgiao/kernel` (`storage.ts`), adapter `S3ObjectStorage` + `UploadService` ở `@tamgiao/db` (`storage/`). - **Hoàn tiền (billing, BE-S4-04):** 2 bước, không gọi cổng trong transaction. (1) **Yêu cầu hoàn** (`startRefund`, một transaction, payment khoá `FOR UPDATE`): `SUCCEEDED → REFUND_PENDING` (`refund_requested_at`) + voucher `RESERVED|ACTIVE` → `VOID('PAYMENT_REFUNDED')` + ledger `VOUCHER_VOID` (voucher đã `REDEEMED` → `VOUCHER_ALREADY_REDEEMED`, không đổi gì). (2) **Gọi cổng** ở worker (lúc làm BE-S4-04 API chưa có pg-boss nên dùng job quét thay vì xếp job trong transaction): cron `billing.refund-dispatch` (mỗi phút) liệt kê `REFUND_PENDING` → `boss.send('billing.refund-payment', {paymentId})` với id job xác định theo payment (mỗi khoản một job). Job `RefundVerificationPayment`: đọc không khoá → không còn `REFUND_PENDING` thì `SKIPPED` → `gateway.refund` ngoài transaction → transaction khoá lại, kiểm tra lại → `completeRefund` (`REFUNDED`) + ledger `REFUND` (unique (payment, `REFUND`)) + `RefundCompleted` qua outbox. Lỗi tạm thời (`retryable`) → throw, pg-boss retry backoff (`retryLimit 10`, `retryDelay 30s`, luỹ thừa + jitter ≈ 8,5–17 giờ, hết lượt → dead-letter log error); lỗi vĩnh viễn → log error (paymentId + loại lỗi), giữ `REFUND_PENDING` cho vận hành. Crash sau khi cổng hoàn nhưng trước commit: lần chạy lại gọi cổng lần nữa, cổng trả "đã hoàn" (`REJECTED`) → giữ `REFUND_PENDING` + log error + cảnh báo SLA để vận hành đối soát (port chưa phân biệt "đã hoàn"; khi chốt D3 nên thêm idempotency key cho `refund`). Route (`requireUser`): `POST /me/dates {partnerId, startsAt, endsAt, staffBookingRequested}` → `ProposeDate`: facade matching `findOpenMatchForUser` (mới, BE-S7-01) phải `DATING` (không có / khác → `MATCH_NOT_DATING` `meta.status`) → khung giờ (`startsAt > now`, `endsAt > startsAt`, sai → `DATE_TIME_INVALID`) → facade quán `BillingPartnerFacade.isActivePartner` (mới, tách khỏi `BillingFacade`; không / tắt → `PARTNER_NOT_FOUND`) → một transaction: lịch mở → `DATE_ALREADY_OPEN` (`meta.datePlanId`) → lưu + `DateProposed` → hẹn job `dating.expire-date-plan` (`DATE_PLAN_EXPIRY_QUEUE`, key `<id>:<version>`, `runAt = expiresAt`; API tạo sẵn queue qua `DATING_SCHEDULED_QUEUES`). Hạn xác nhận `expiresAt = min(proposedAt + DATE_RESPONSE_TTL_HOURS, startsAt)`. `POST /me/dates/:id/confirm` (`ConfirmDate`: người ngoài → `NOT_PARTICIPANT` trước; match của lịch phải còn là match mở `DATING` của người dùng → không: `MATCH_NOT_DATING`; khoá `FOR UPDATE`; người mời → `DATE_NOT_INVITEE`; không còn `PROPOSED` → `DATE_INVALID_TRANSITION`; `now >= expiresAt` → `DATE_RESPONSE_EXPIRED`) → `DateConfirmed {datePlanId, matchId, inviterId, inviteeId, partnerId, startsAt, endsAt, staffBookingRequested}`; `…/decline` → `DECLINED`; `…/cancel` (một trong hai người, chỉ `CONFIRMED`, `now <= startsAt − DATE_CANCEL_CUTOFF_HOURS`, quá → `CANCEL_TOO_LATE` của verification) → `CANCELLED` (voucher đã kích hoạt giữ nguyên); `GET /me/dates/current` = lịch mới nhất của match đang mở (mọi trạng thái). Worker: job `ExpireDatePlan.executeIn` (khoá, `PROPOSED` quá hạn → `EXPIRED` + `DateExpired`; còn lại no-op) → đề xuất lịch mới được. **Billing** consumer `billing.activate-voucher-on-date-confirmed` (`ActivateVoucherOnDateConfirmed`, đăng ký trong `createBillingWorker`): voucher `RESERVED` của **người mời** (`inviterId`, mặc định khi D1 chưa chốt) → `ACTIVE` + `VoucherActivated`; đã có voucher `ACTIVE` → no-op; không có voucher mở / quá hạn dùng → no-op; voucher chưa có hạn dùng (`KycApproved` chưa xử lý) → throw để hàng đợi thử lại. Không gắn quán vào voucher khi xác nhận (lịch có thể bị huỷ).

- **Composition root:** mỗi module export `createXModule(deps)` trả về `{ routes, handlers, facade }`; `apps/api/src/main.ts` và `apps/worker/src/main.ts` nối thủ công (không dùng DI container).
- **Xác thực người dùng app:** access token JWT HS256 15 phút (claims `sub`=userId, `sid`=sessionId) + refresh token ngẫu nhiên 256-bit chỉ lưu SHA-256 (`identity.refresh_tokens`), xoay vòng mỗi lần dùng; token đã dùng bị dùng lại → thu hồi cả phiên (`identity.sessions`, một phiên = một thiết bị). Middleware `requireUser(authenticate)` nằm ở `@tamgiao/http`, nhận hàm `identity.facade.authenticateUser` (kiểm tra chữ ký, hạn **và** phiên chưa thu hồi) và gắn `c.get('auth') = { userId, sessionId }`; module khác dùng lại middleware này, không tự đọc token.
- **Xác thực admin:** email + mật khẩu argon2id + TOTP (RFC 6238, secret mã hoá `totp_secret_enc`, chặn dùng lại mã) — thiếu một trong hai không đăng nhập được; sai 5 lần khoá 15 phút. Token phiên dạng opaque (DB chỉ lưu SHA-256, `identity.admin_sessions`), 8 giờ / 12 giờ nếu "ghi nhớ thiết bị". Bảng role → permission ở `identity/domain/permissions.ts` (tên permission xuất lại ở `@tamgiao/contracts`). Route admin của mọi module gắn guard `identity.requireAdmin('<permission>')` (do composition root truyền vào): 401 nếu chưa đăng nhập, 403 `FORBIDDEN` nếu role thiếu quyền; role đọc lại từ DB mỗi request. Seed admin đầu tiên: `pnpm --filter @tamgiao/tools seed:admin --email <email> --role ADMIN`.
- **Audit log:** module cần ghi vết nhận `identity.auditLogger` (kiểu `AuditLogger` từ `@tamgiao/module-identity/facade`) qua composition root và gọi `log(tx, {actor, action, targetType, targetId, ip, meta})` — truyền `tx` để bản ghi audit commit/rollback cùng thao tác. `action` dạng `<miền>.<hành động>` (vd `kyc.view_detail`); `meta` chỉ chứa JSON không nhạy cảm, khoá có tên gợi PII (`phone`, `cccd`, `income`, `email`, `message`…) bị từ chối `AUDIT_ENTRY_INVALID`. Bảng `identity.audit_logs` chỉ ghi thêm: trigger cấp câu lệnh chặn mọi UPDATE/DELETE (kể cả role owner mà app đang dùng) + REVOKE khỏi PUBLIC. Admin xem qua `GET /admin/audit-logs` (permission `audit:read`, lọc actor/target/thời gian, phân trang cursor).
- **Lỗi HTTP:** Problem JSON (RFC 7807) `{ type, title, status, code, detail, traceId }`; map `code` → status tại presentation.
