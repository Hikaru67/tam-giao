# Kiến trúc Backend — Tâm Giao

Clean Architecture + Modular Monolith, TypeScript. Tài liệu này là nguồn chân lý về thiết kế;
luật bắt buộc rút gọn nằm ở `AGENTS.md` mục 2.

## 1. Tổng quan hệ thống

```
Mobile (Expo) ─┐
Admin (Next.js)├─ HTTPS / WebSocket ─► apps/api (Hono) ──┬─ PostgreSQL (schema theo module, outbox)
Partner web ───┘                                        ├─ Redis (pub/sub chat, từ Sprint 6)
                                                        ├─ Object storage S3 (bucket public-profile / private-kyc)
                      apps/worker (pg-boss) ◄── outbox ─┘
                      job hết hạn, relay event, push, retention
Bên ngoài: SMS OTP · eKYC · Cổng thanh toán · Push (Expo/FCM/APNs) · KMS
```

## 2. Các lớp và quy tắc phụ thuộc

```
infrastructure ─► application ─► domain ─► kernel
presentation   ─► application
(phụ thuộc chỉ hướng vào trong)
```

| Lớp | Chứa | Được import |
|---|---|---|
| `domain` | Aggregate, Entity, Value Object, Domain Service, Domain Event, mã lỗi | `@tamgiao/kernel`, `@tamgiao/contracts/constants` |
| `application` | Use case, Query, Port (interface), Facade cho module khác | `domain`, `kernel`, `contracts/constants`, `@tamgiao/module-<khác>/facade` |
| `infrastructure` | Repository (Drizzle), adapter bên ngoài, mapper, schema DB, job handler | tất cả ở trên + thư viện |
| `presentation` | Route Hono, WS handler, map DTO ↔ command, map lỗi → HTTP | `application`, `contracts` |

## 4. Module

| Module | Trách nhiệm | Mức độ |
|---|---|---|
| identity | OTP, session/JWT, admin user, 2FA, RBAC, audit log | đủ lớp |
| profile | Hồ sơ, ảnh, tiêu chí bạn đời, trạng thái onboarding | mỏng |
| verification | eKYC, duyệt độc thân, phỏng vấn sơ bộ | đủ lớp |
| billing | Thanh toán, ledger, hoàn tiền, voucher, partner | đủ lớp |
| matching | Gợi ý, máy trạng thái, độc quyền 1-1, cooldown, chấm điểm | đủ lớp (lõi) |
| messaging | Chat 14 ngày, lọc lừa đảo, che SĐT/link | đủ lớp |
| dating | Đặt hẹn, check-in an toàn, đánh giá sau gặp | đủ lớp |
| safety | Báo cáo vi phạm, khoá 2 chiều, kiểm duyệt | đủ lớp |
| notification | Push, SMS, template | mỏng |

Giao tiếp giữa module: **domain event qua outbox** (bất đồng bộ) hoặc **facade read-only** (đồng bộ).

### Event chính

| Event | Phát bởi | Tiêu thụ bởi |
|---|---|---|
| `PaymentSucceeded` | billing | verification (cho phép nộp), notification |
| `KycApproved` / `KycRejected` | verification | matching (đủ điều kiện), billing (hoàn tiền khi rejected), notification |
| `MatchOffered` / `MatchAwaitingResponse` | matching | notification |
| `MatchStartedDating` | matching | messaging (mở hội thoại), notification |
| `MatchClosed` (success/stopped/expired/locked) | matching | messaging (đóng hội thoại), notification |
| `DateConfirmed` | dating | billing (kích hoạt voucher), notification |
| `FeedbackSubmitted` | dating | matching (chuyển CLOSED_*) |
| `ReportFiled` | safety | matching (LOCKED), messaging (đóng), notification (alert chuyên viên) |

## 5. Máy trạng thái Match

```
OFFERED ──accept(1 bên)──► AWAITING_RESPONSE ──accept(bên còn lại)──► DATING ──date xong──► MET
  │ decline / hết 24h          │ decline / withdraw / hết 24h            │ stop / hết 14 ngày      │ feedback
  ▼                            ▼                                         ▼                         ▼
EXPIRED | DECLINED          DECLINED | EXPIRED                      CLOSED_STOPPED          CLOSED_SUCCESS (cả 2 chọn A)
                                                                     → COOLDOWN 7 ngày       CLOSED_STOPPED (≥1 chọn B)
Mọi trạng thái chưa đóng ──ReportFiled──► LOCKED
```

- **Độc quyền 1-1:** bảng `matching.active_slots(user_id PK, match_id)`. Tạo match = insert 2 dòng trong cùng `tx`; trùng → `USER_BUSY`. Đóng match = xoá 2 dòng.
- **Cooldown:** `matching.cooldowns(user_id PK, until)`.
- **Hết hạn:** mỗi lần chuyển trạng thái có hạn → `Scheduler.schedule(tx, matchExpiryJob(match))` (queue `matching.expire-match` = `MATCH_EXPIRY_QUEUE`, key `<matchId>:<version>`, `runAt = expiresAt`, payload `{matchId}`); job gọi `ExpireMatch` (kiểm tra lại state + thời gian, idempotent).
- **Bảng match (BE-S5-04):** `matching.matches` — đủ cột dựng lại `MatchState`: hai người lưu 2 cột `user_a`/`user_b` (giữ thứ tự lúc đề xuất; cặp luôn đúng 2 người nên CHECK `user_a <> user_b` và index btree từng cột đơn giản hơn mảng), `created_by` (admin), `status` (CHECK 9 trạng thái), `accepted_by uuid[]` (≤ 2), `score_snapshot` jsonb `{total, pillars}`, `staff_note` (có thể PII — không log, không vào event/audit), `expires_at` nullable, `offered_at`/`dating_started_at`/`met_at`/`closed_at`, `declined_by`, `decline_reason`, `withdrawn`, `close_outcome` (CHECK), `lock_reason`, `updated_at`, `version`. `DrizzleMatchRepository.save` kiểm tra version lạc quan (version trước = version − số event chờ: `0` → INSERT, khác → `UPDATE … WHERE version = <trước>`, lệch → throw) rồi ghi mỗi event một dòng `matching.match_events` (`id` = eventId, `match_id` FK, `event_type`, `payload` jsonb như outbox, `occurred_at`, `version`, unique (`match_id`, `version`); **append-only**: trigger cấp câu lệnh chặn UPDATE/DELETE như `billing.ledger_entries`) + outbox, cùng `tx`. Có `findById`, `findByIdForUpdate` (`FOR UPDATE`), `findOpenByUser`.
- **Đề xuất ghép đôi (BE-S5-04):** use case `ProposeMatch` (`createMatchingModule(...).commands.proposeMatch`; route admin + permission `match:propose` ở BE-S5-07). Thứ tự: cùng một người → `MATCH_SAME_USER`; id không phải UUID v7 → `INVALID_ID`; chưa xác thực → `USER_NOT_VERIFIED` (`meta.userIds`) — đọc `VerificationFacade.isVerified` (nguồn chân lý, ngoài transaction) thay vì cờ `verified` của read model (đồng bộ trễ qua event); rồi **một transaction**: chưa có hồ sơ đồng bộ trong `candidate_profiles` → `CANDIDATE_PROFILE_NOT_FOUND` (`meta.userIds`); vi phạm `passesHardFilters` → **chặn** `HARD_FILTER_MISMATCH` (tiêu chí bắt buộc do chính người dùng đặt, chuyên viên không vượt); cooldown → `USER_COOLING_DOWN`; `pair_history` → `PAIR_ALREADY_TRIED`; `CompatibilityScorer` → snapshot; `Match.offer` → `activeSlots.claim([A,B])` (bận → `USER_BUSY`, Err → rollback: không match, không job) → `matches.save` (+ `match_events` + outbox `MatchOffered`) → job hết hạn → audit `match.propose` (meta `{participantIds, scoreTotal, hasStaffNote}`, không ghi nội dung ghi chú; audit bị từ chối → throw, rollback). Hai chuyên viên đề xuất đồng thời cho cùng một người → PK `active_slots` cho đúng 1 thành công.
- **Query màn ghép đôi (BE-S5-06, `createMatchingModule(...).queries`; route ở BE-S5-07):** `getCurrentMatch` (`GetCurrentMatchForUser`, màn 7/9) — match mở qua `MatchRepository.findOpenByUser`; không có → `null`; trả `status`, `phase` nhìn từ người xem (`NEEDS_MY_RESPONSE` = `OFFERED`; `AWAITING_RESPONSE` → `WAITING_FOR_COUNTERPART` nếu mình đã đồng ý / `COUNTERPART_ACCEPTED` nếu đối phương đã đồng ý; `DATING`; `MET`), `expiresAt` = đúng `matches.expires_at`, điểm tổng + 3 trụ cột từ `score_snapshot`, `staff_note` (chỉ người trong cặp), thẻ đối phương. `getMatchProfile` (`GetMatchProfile`, màn 8) — theo `matchId` hoặc match đang mở; thứ tự: id sai → `INVALID_ID`, không có → `NOT_FOUND`, **không thuộc cặp → `NOT_PARTICIPANT`** (trước khi xét trạng thái), match đã đóng → `NOT_FOUND`. **Luật hiển thị cho người dùng app** (`application/queries/match-display-rules.ts`): chỉ phần công khai của hồ sơ — tên gọi (`displayNameOf`: bỏ họ khi ≥ 3 từ, như thiết kế "Minh Trang, 28"; không trả họ tên đầy đủ), tuổi, giới tính, thành phố, nghề, học vấn, tự bạch, sở thích, ảnh hồ sơ (presigned GET `publicProfile`); không bao giờ trả SĐT, CCCD, thu nhập/nhà ở/tài sản, ảnh eKYC; phần riêng tư "mở sau bước đồng ý" chưa trả (chờ chốt luật). **Điểm chung** không lưu trong snapshot → tính lại bằng `CompatibilityScorer` trên read model `candidate_profiles` lúc đọc (thiếu hồ sơ → rỗng); phía người dùng bỏ `SAME_RELIGION` (tôn giáo là dữ liệu nhạy cảm theo NĐ 13), admin thấy đủ. Hồ sơ hiển thị lấy qua facade profile `getMatchDisplayProfiles(userIds, {photos: 'all'|'primary'})` (chỉ hồ sơ `COMPLETED`, chỉ cột không mã hoá). Admin: `listCandidates` (`ListCandidates`) = `FindCandidates` + hồ sơ hiển thị (họ tên đầy đủ, tuổi, thành phố, nghề, học vấn, ảnh đại diện; mặc định 20, tối đa 50); `getMatchesBoard` (`GetMatchesBoard`, port `MatchBoardQuery` → `DrizzleMatchBoardQuery`) lọc trạng thái (mặc định 4 trạng thái mở), sắp `expires_at ASC NULLS LAST, id ASC`, cursor keyset `{expiresAt|null, id}` (presentation mã hoá), tên hai người qua `getApplicantSummaries`, không trả `staff_note`/lý do từ chối.

## 6. Pattern hạ tầng

- **UnitOfWork:** `uow.run(async tx => …)` bọc `db.transaction`.
- **Outbox:** `outbox(id, event_type, payload, occurred_at, published_at)`; worker relay → EventBus nội bộ → handler; `processed_events(consumer, event_id)` đảm bảo idempotent.
- **Scheduler:** pg-boss, job key = `<type>:<aggregateId>:<version>` để không trùng (`PgBossScheduler`: id job = UUID v5 của `<queue>:<key>`, gửi bằng chính connection của `tx` → rollback thì không có job). **API** (từ BE-S5-04) dựng một instance pg-boss **chỉ để gửi job** (`apps/api/src/job-scheduler.ts`: `supervise: false`, `schedule: false`, không worker; `migrate` mặc định) và tạo sẵn các queue mà API gửi (`MATCHING_SCHEDULED_QUEUES`) cùng cấu hình `ensureQueue` của worker (`DEFAULT_RETRY_POLICY` + dead-letter `<queue>.dead`; `createQueue` là `ON CONFLICT DO NOTHING`), đóng khi shutdown. Worker chạy handler + bảo trì.
- **Encryptor:** envelope encryption AES-256-GCM; master key từ KMS (local: env). Blind index HMAC-SHA256 cho tìm kiếm CCCD.
- **Storage:** presigned PUT/GET; bucket `public-profile` (ảnh hồ sơ, vẫn cần auth để lấy URL) và `private-kyc` (CCCD, selfie, bằng chứng). Port `ObjectStorage` + `UploadRegistry` ở `@tamgiao/kernel` (`storage.ts`), adapter `S3ObjectStorage` + `UploadService` ở `@tamgiao/db` (`storage/`). Luồng: app gọi `POST /uploads {purpose, contentType, sizeBytes}` → server kiểm tra MIME (jpeg/png/heic) và kích thước (≤ 10 MB) rồi ghi `platform.uploads` (`PENDING`) và trả presigned PUT có ký `content-type` + `content-length` (TTL `PRESIGNED_URL_TTL_SECONDS`) → app PUT thẳng lên storage → gửi `key` cho API nghiệp vụ → module gọi `uploads.verifyOwned(tx, {ownerId, key, purposes})` (sai chủ → `UPLOAD_NOT_OWNED`; sai mục đích / chưa tải lên / object khác khai báo → `UPLOAD_INVALID`; thành công → `CONFIRMED`). Key dạng `<purpose>/<ownerId>/<uploadId>.<ext>`, không chứa tên tệp gốc.
- **Hồ sơ (profile):** `PUT /me/profile` gửi toàn bộ form; `submit: false` = "Lưu tạm" (chấp nhận form dở, nhưng trường đã điền vẫn phải hợp lệ), `submit: true` = "Tiếp tục" (bắt buộc đủ trường, `PROFILE_INCOMPLETE` + `meta.missing`); lần hoàn tất đầu tiên phát `ProfileCompleted` qua outbox, hồ sơ đã hoàn tất không quay lại nháp. Tuổi tính theo ngày lịch Việt Nam (UTC+7) so với `MIN_AGE`. `photos` ≤ `MAX_PROFILE_PHOTOS`, phần tử đầu là ảnh đại diện, mỗi key xác nhận qua `UploadRegistry`. Thu nhập/nhà ở/tài sản lưu `*_enc` (context `profile.profiles.<cột>:<userId>`).
- **Tiêu chí bạn đời:** `profile.preferences` — bộ lọc cứng (`age_min`, `age_max`, `area_city`, `area_radius_km`, `children_plan`, `religion`, `min_education`) là cột riêng để matching lọc bằng SQL; lối sống, độc lập tài chính, 3 phẩm chất cốt lõi ở jsonb `details`. Giá trị `not_important` = bỏ qua tiêu chí. Mỗi lần lưu phát `PreferencesUpdated`.
- **Read model ứng viên + chấm điểm tương hợp (matching, BE-S5-03):** bảng `matching.candidate_profiles` (`user_id` PK; cột lọc cứng `gender`, `birth_date`, `city_key`, `education`, `children_plan`, `religion`, `pref_age_min|max`, `pref_city_key`, `pref_min_education`; jsonb `scoring {lifestyle, financialIndependence, coreTraits}`; cờ `verified`; `profile_version`/`preferences_version`; CHECK `num_nulls(...) in (0, 12)` = phần hồ sơ đủ hết hoặc chưa có gì). Không chứa họ tên, ảnh, tự bạch, dữ liệu mã hoá (thu nhập/nhà ở/tài sản). Đồng bộ bằng consumer worker (`createMatchingWorker`): `matching.candidate-on-profile-completed` / `matching.candidate-on-preferences-updated` đọc lại `ProfileFacade.getMatchingProfile` (hồ sơ `COMPLETED` + có tiêu chí; worker dựng bằng `createMatchingProfileReader({uow})`, không cần `Encryptor`) rồi upsert — chỉ ghi khi cả hai version nguồn ≥ bản đang lưu (consumer song song không ghi lùi); `matching.candidate-on-kyc-approved|rejected` đặt `verified` true/false (APPROVED/REJECTED là trạng thái cuối của eKYC nên lấy từ event là đúng). Thành phố chuẩn hoá `cityKey` (NFC, gộp khoảng trắng, chữ thường). **Bộ lọc cứng** (`passesHardFilters` ở domain; `DrizzleCandidateFinder` viết lại bằng một câu SQL tự join, test tích hợp đối chiếu trên lưới mẫu): hai chiều tuổi (`age(ngày VN, birth_date)` trong khoảng của người kia) và khu vực (`pref_city_key` null = không giới hạn; bán kính chưa áp dụng vì chưa có toạ độ); tôn giáo/con cái so khớp **đối xứng** hai giá trị tiêu chí (hồ sơ không có trường riêng): `not_important` bỏ qua, con cái `open` hợp mọi lựa chọn, còn lại phải trùng; giới tính: **chỉ ghép khác giới** (`gender` khác nhau — quyết định PO khi review BE-S5-03). Tôn giáo/con cái hiện so tiêu chí hai bên vì hồ sơ chưa có trường riêng — PO đã chốt bổ sung trường vào hồ sơ (task BE-S6-07), khi đó đổi sang so hồ sơ ↔ tiêu chí. Loại: chính mình, chưa `verified`, chưa đồng bộ hồ sơ, có dòng `active_slots`, `cooldowns.until > now`, có `pair_history` (cặp `least/greatest`). **`CompatibilityScorer`** (domain service thuần, đối xứng, toàn số nguyên, làm tròn nửa lên): 3 trụ cột `VALUES_FAMILY` (tôn giáo, phẩm chất cốt lõi trùng), `PLANS_TIMING` (con cái, độ lệch khỏi tâm khoảng tuổi mong muốn hai chiều, cùng thành phố), `LIFESTYLE_FINANCE` (4 thói quen theo thứ bậc, quan điểm độc lập tài chính, học vấn tối thiểu hai chiều) → tổng 0–100 có trọng số; trọng số + thang điểm ở `domain/compatibility-weights.ts`; điểm chung là mã (`SAME_RELIGION`, `SHARED_TRAIT_<TRAIT>`…), không PII. Use case `FindCandidates` (`createFindCandidates`): nạp tối đa `CANDIDATE_POOL_SIZE` = 500 ứng viên qua lọc cứng, chấm điểm, sắp điểm giảm dần (hoà → `userId`), trả top N ≤ 50; người tìm chưa có trong read model → `CANDIDATE_PROFILE_NOT_FOUND`.
- **Nộp eKYC (verification):** `POST /me/kyc {cccdFrontKey, cccdBackKey, selfieKey, maritalStatusCertificateKey}` (thiếu → `KYC_DOCS_MISSING` + `meta.missing`). Use case `SubmitKyc` chạy 2 transaction ngắn, gọi eKYC ở giữa (không giữ connection khi chờ nhà cung cấp): (1) kiểm tra hồ sơ còn được nộp (chưa có, hoặc `NEEDS_MORE_INFO` → nộp bổ sung; các trạng thái khác kể cả `REJECTED` → `KYC_ALREADY_SUBMITTED`) + `uploads.verifyOwned` (`kyc_doc` cho CCCD/giấy độc thân, `kyc_selfie` cho selfie); (2) gọi song song `ocrIdCard`/`checkLiveness`/`matchFace` qua `ResilientEkycProvider` — bị từ chối (ảnh mờ, không khớp) hay lỗi hạ tầng (timeout) đều **vẫn nộp**, kết quả từng thao tác + điểm lưu ở `ekyc_assessment` làm gợi ý; họ tên/ngày sinh OCR đối chiếu với facade profile (bỏ dấu, viết hoa, gộp khoảng trắng), lệch → cờ `profileMismatches`, không chặn; **không bước nào tự đánh `PASSED`** (chuyên viên quyết định); (3) khoá theo user (advisory lock) rồi lưu `verification.kyc_submissions` + `KycSubmitted` vào outbox. Số CCCD lưu `cccd_number_enc` (context `verification.kyc_submissions.cccd_number:<userId>`) + `cccd_number_bidx` UNIQUE (purpose `verification.cccd_number`); vi phạm unique (23505) map theo tên constraint → `CCCD_ALREADY_REGISTERED` / `KYC_ALREADY_SUBMITTED` (Result, không 500). `GET /me/kyc` luôn 200: `NOT_SUBMITTED` khi chưa nộp, đủ 4 bước theo thứ tự `CCCD_CHIP, MARITAL_STATUS, MANUAL_REVIEW, INTERVIEW`, mục cần bổ sung khi `NEEDS_MORE_INFO`; không trả số CCCD/điểm eKYC. Dev dùng `FakeEkycProvider({ deriveCccdFromKey: true })` để mỗi user có số CCCD giả khác nhau.
- **Phỏng vấn sơ bộ (verification):** bảng `verification.interview_slots` (slot `INTERVIEW_DURATION_MINUTES` phút, `OPEN → BOOKED → COMPLETED`, huỷ thì `BOOKED → OPEN`). Chuyên viên (`kyc:review`) mở slot `POST /admin/kyc/interview/slots {startsAt, meetingUrl?}` (không chồng giờ với slot khác của mình: advisory lock theo chuyên viên + unique `interviewer_id, starts_at` → `INTERVIEW_SLOT_OVERLAP`), xem nhật ký `GET /admin/kyc/interview/slots?status&from&to&limit`, ghi kết quả `PUT /admin/kyc/interview/:id/notes {outcome, notes}` — cùng transaction gọi `KycSubmission.markStep('INTERVIEW', outcome)` (hồ sơ đã quyết định → `KYC_ALREADY_DECIDED`); chỉ ghi khi slot đã đặt và đã tới giờ bắt đầu. Người dùng: `GET /me/kyc/interview/slots` (slot trống, không lộ chuyên viên/link), `GET|POST|PUT|DELETE /me/kyc/interview` (xem/đặt/đổi/huỷ). - **Hoàn tiền (billing, BE-S4-04):** 2 bước, không gọi cổng trong transaction. (1) **Yêu cầu hoàn** (`startRefund`, một transaction, payment khoá `FOR UPDATE`): `SUCCEEDED → REFUND_PENDING` (`refund_requested_at`) + voucher `RESERVED|ACTIVE` → `VOID('PAYMENT_REFUNDED')` + ledger `VOUCHER_VOID` (voucher đã `REDEEMED` → `VOUCHER_ALREADY_REDEEMED`, không đổi gì). Hai nguồn: consumer `billing.refund-on-kyc-rejected` (event `KycRejected`; không có khoản `SUCCEEDED` → bỏ qua — cùng `processed_events` là 2 lớp idempotent) và admin `POST /admin/payments/:id/refund {reason}` (`billing:refund`, lý do 1–500 ký tự chỉ lưu ở audit `billing.refund_request` cùng `tx`, 202; đang/đã hoàn → `PAYMENT_ALREADY_REFUNDED`, không tồn tại → `PAYMENT_NOT_FOUND`). (2) **Gọi cổng** ở worker (lúc làm BE-S4-04 API chưa có pg-boss nên dùng job quét thay vì xếp job trong transaction): cron `billing.refund-dispatch` (mỗi phút) liệt kê `REFUND_PENDING` → `boss.send('billing.refund-payment', {paymentId})` với id job xác định theo payment (mỗi khoản một job). Job `RefundVerificationPayment`: đọc không khoá → không còn `REFUND_PENDING` thì `SKIPPED` → `gateway.refund` ngoài transaction → transaction khoá lại, kiểm tra lại → `completeRefund` (`REFUNDED`) + ledger `REFUND` (unique (payment, `REFUND`)) + `RefundCompleted` qua outbox. Lỗi tạm thời (`retryable`) → throw, pg-boss retry backoff (`retryLimit 10`, `retryDelay 30s`, luỹ thừa + jitter ≈ 8,5–17 giờ, hết lượt → dead-letter log error); lỗi vĩnh viễn → log error (paymentId + loại lỗi), giữ `REFUND_PENDING` cho vận hành. Cron `billing.refund-sla-check` (15 phút) log **error** `alert: 'refund_sla_breached'` cho mỗi khoản `REFUND_PENDING` có `refund_requested_at <= now − REFUND_SLA_HOURS` (không PII). Crash sau khi cổng hoàn nhưng trước commit: lần chạy lại gọi cổng lần nữa, cổng trả "đã hoàn" (`REJECTED`) → giữ `REFUND_PENDING` + log error + cảnh báo SLA để vận hành đối soát (port chưa phân biệt "đã hoàn"; khi chốt D3 nên thêm idempotency key cho `refund`). Consumer `billing.set-voucher-expiry` (event `KycApproved`): voucher `RESERVED|ACTIVE` chưa có hạn → `expires_at = occurredAt của event + VOUCHER_TTL_DAYS` (đúng "ngày duyệt", không lệch theo độ trễ relay); đã có hạn → bỏ qua. Worker dùng `FakePaymentGateway({ acceptUnknownRefunds: true })` (instance khác API nên không biết giao dịch; config worker cấm `fake` ở production).
